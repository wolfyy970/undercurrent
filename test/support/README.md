# Model output in tests

There is no fake or replay model in `src/`, and no test serves hand-written assistant text. A test that needs a model
reply serves a **recorded real reply** (`recordedModel.ts`, below) to the engine's production client over
`LLM_API_URL`. Everything else a local server sends is an **HTTP or wire-format fixture**: errors, timeouts, framing,
or a placeholder body around which the client's own behaviour is pinned (table at the end). Record runs are guarded:
`UC_RECORD_MAX_CALLS` (default 8) and `UC_RECORD_MAX_USD` (default 0.008) per scenario, the `recordMaxCalls` option
for a tighter cap, and `UC_RECORD_LEDGER_CAP_USD` against the ledger total; a guarded request gets HTTP 400
"record guard".

## Recorded real replies

`recordedModel.ts` serves recordings from `test/fixtures/recordings/<suite>/<scenario>.json` to the engine's
production client (`LlmCliClient`, the port's `llm`) over `LLM_API_URL`. Each file carries `source`, `provider_url`,
`model`, `recorded_at`, and every call's request body, raw response body, usage and an upper-bound cost. Re-record
with `UC_RECORD=1 UC_RECORD_ONLY='<suite>/<scenario regex>' DEEPSEEK_API_KEY=… npx vitest run <file>`; a request with
no recording is answered HTTP 400 "recording miss" (terminal) and `verify()` throws. Scenarios named `transport-*`
and `httpFixtures` entries are HTTP fixtures, never recorded and never model text.

## Parity harnesses

Every harness under `parity/` that has a model leg runs each side's real `llm` client against one replay server:
`parity/execlines`, `parity/responder`, `parity/behavioral`, `parity/recap` (main, adversarial, seal-trigger),
`parity/retrieval`, `parity/mem`, `parity/init`, `parity/lostwake` and `parity/fuzz` (recap, mem), rows above.
`parity/slack`, `parity/telegram` and `parity/sandbox` have no model leg on either side: they are no-model layers,
labelled in their headers, and their fake Slack/Telegram/web servers and the sandbox's reachability listener are HTTP
transport fixtures. The responder harness also has two layers with no model at all: redaction (upstream's
`_redact_card`/`_redact_keys` vs the port's functions) and parser (upstream's reply-handling section, cut from the
step file at run time by markers and checked by byte length and sha256, vs `interpretReply`, on literal reply
strings). recap's parser layer (`run-parser-parity.mjs`) does the same for upstream's `_llm_json`.
