## Verdict

### Real port bug (undocumented): U+007F (DEL) not escaped

**jq escapes U+007F as `\u007f`; Node `JSON.stringify` emits the raw 0x7f byte.** Confirmed by an exhaustive codepoint scan (0x01..0x2FFFF) as the *only* escaping divergence between the two serializers — every C0 control (0x00..0x1f) escapes identically and every char >= 0x80 is emitted literally by both. It surfaces at BOTH JSON-emitting call sites: the final `JSON.stringify(mergeRoles(msgs), null, 2)` (scenario `control-char-del-0x7f`) and `ppValue` for object/array content fields (`del-0x7f-in-object-field`).

Reachable: step `content`/`stdout`/`stderr` come from real shell output, which can contain a 0x7f byte. When it does, the port's output differs byte-for-byte from Bash. Severity is LOW — both encodings are valid JSON for the *same* string, so any JSON parser (`llm -M`) yields identical messages; only the byte-exact "identical to jq" claim breaks. But it is a genuine port bug, not a documented deviation.

**Minimal fix** (in `src/context.ts`; do not rely on `JSON.stringify` alone): route every final/pp serialization through a jq-faithful helper that also escapes 0x7f, e.g.

```ts
const jqJson = (v: unknown) => JSON.stringify(v, null, 2).replace(/\x7f/g, "\\u007f");
// use in ppValue() AND at the renderMsgs() `JSON.stringify(mergeRoles(msgs), null, 2)`
```
Both sites are required: an object/array content field serializes through two levels (`ppValue` produces the field string, then the messages array re-serializes it), and jq escapes 0x7f at each level (inner `x\u007fy` → outer `x\\u007fy`). Verified: with the helper at both sites, the port reproduces jq byte-for-byte on the plain-string path and the nested object-field path; it is a no-op on all 103 currently-passing scenarios. Applying it inside `renderMsgs` also fixes `--max-bytes` accounting (Bash counts the 6-byte `\u007f`, so the port must too). 0x7f is the sole divergent codepoint, so this is the complete fix.

### Divergences that are NOT port bugs (degenerate / malformed / platform inputs)

1. **`${2:?}` stderr wording** (missing/empty required flag value) — deliberate documented deviation; exit(1)+empty stdout+state match.
2. **Non-object JSONL line** (number/array/string/bool) — Bash aborts (jq `.step_id` error, exit 5), port drops the line and continues; documented deviation #3; real lines are always objects.
3. **Multi-dir hex-prefix tie-break** — `find|head -1` vs DFS; documented deviation #2; filesystem-order dependent on both sides; real dirs hold a single `<hex8>-root`.
4. **`--max-bytes 0`** — BSD `head -c 0` errors (macOS, exit 1); GNU head is SIGPIPE-timing-dependent under `pipefail`; the port is deterministic (empty + budget marker + exit 0). Platform/shell artifact on a degenerate input (no caller passes 0), harmless on the Linux target.
5. **`step_id: false`** — jq `//` drops it, port `??` keeps it; undocumented micro-gap on an absurd value step_id never takes. (Same `//`-vs-`??` root as any `false`-valued `type`/`step_id`; content `from_branch` correctly uses `//` semantics.)
