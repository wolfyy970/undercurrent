# RUNTIME-SEAMS — process/container-boundary audit

Grep-driven inventory of every runtime construct in the upstream Bash
(`<upstream>/bin/shellm`, `bin/shellm-docker`, `bin/thinkers`,
`thinkers/{monolith,retrieval,responder}/step`, `thinkers/_lib/common.sh`,
`tools/headlong-killall`, `tools/identity`, `bin/chat`, `bin/mem`, `bin/traj`,
`bin/recap`, `bin/llm`), mapped to its port counterpart, with the mode under
which it is actually proven. Today's side-by-side run found four port bugs
that every unit harness had missed because all four sit at RUNTIME SEAMS —
a file written during Docker-sandboxed exec at a host-only path, a detached
subshell that must outlive the step, log redirects that carried no content,
and `_kill_tree`/`--force` semantics. This file is the search for the next
ones, before a live run finds them.

**Method note on tooling.** `src/recap.ts` contains a literal NUL byte inside
a comment (documenting jq's own NUL handling), which makes this checkout's
`grep` (aliased to `ugrep`) treat the file as binary and silently return zero
matches with no warning. Every grep-based claim below about `src/recap.ts`
was re-run with `grep -a` after that was discovered; no other port file in
`src/` triggered the same false negative (checked via `file src/*.ts
src/*.mjs`). Anyone repeating this audit should assume the same trap.

**Update (this pass).** The same trap is wider than `src/` alone: `test/recap.test.ts` (imports/embeds `src/recap.ts` content) and, separately, `PARITY.md` itself (5700+ lines, long single-line table rows) BOTH also silently zero-match plain `grep` — `PARITY.md` even though `file` reports it as plain UTF-8 text, not binary. Confirmed via `grep -c` vs `grep -ac` returning different counts on both files. Anyone grepping `PARITY.md` or `test/recap.test.ts` in this repo should use `grep -a` (or `grep -c` first as a canary) rather than trusting a silent zero-match.
